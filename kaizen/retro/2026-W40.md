### 学んだこと(3 つ以内)

1. **今週いちばん重要な事実は「数字が 1 つも無い」こと**。指標表が空なのは「今週は横ばいだった」
   という意味ではなく、**改善ループが観測なしで回っている**という意味。この状態では POLICY の
   「指標で語れない変更は出荷しない」が、結果として「何も出荷できない」と同義になる。
2. **週次ダイジェストの前提と日次ワークフローの実装が噛み合っていない可能性がある**(不確実)。
   `kaizen-weekly.yml` は「daily が前日までに書いた metrics(main にマージ済み)」から草稿を作るが、
   日次側で `kaizen/metrics/` が main に入るのは、日次エージェントが PR を作り(`kaizen/prompts/daily.md` §50)
   **その PR がマージされたとき**だけ。日次エージェントの起動自体が `KAIZEN_ENABLED` /
   未マージ PR ゼロ / `sessions ≥ 200` で閉じているので、「1 度も起動していない」と
   「起動したが metrics が main に入らない」を、この週次実行の権限からは区別できない。
   Actions の実行履歴とリポジトリ変数は確認できなかった(`gh run list` / `gh variable list` が未許諾)。
3. **ルール刷新は BACKLOG を腐らせる**。`sq3 の重み`・`pieces.pity.threshold`・`fitGuarantee` の 3 件は、
   刷新で設定キーごと消えている(`src/config/game-config.json` と `src/core/` のどちらにも無い)。
   刷新 PR で BACKLOG と HYPOTHESES を同時に直していれば防げた。今週この 3 件を差し替えた。

### 来週の狙い(種類のローテーション)

今週の出荷が 0 件なので、POLICY の「同じ種類を 3 日連続で選ばない」制約は効いていない。
データが無い前提で、**計測を前提にしない種類**から選ぶ。

1. **実験は 1 件も起票しない**。POLICY「効果が 10 % 未満と見込む実験は 1 日の新規 install が
   500 を超えるまで起票しない」に、現状(install 数が観測不能)は当然に含まれる。
   BACKLOG 上位の実験 7 件はすべて**計測の回復待ち**として据え置く。
2. 優先は **fix → perf**。どちらも実データではなく `npm test` / `npm run sim` / サイズ予算で
   ローカルに検証できるので、テレメトリが無い週でも誠実に出荷判断ができる。
3. **rule / fx / copy は来週は選ばない**。これらは「良くなった」を指標以外で言えない種類で、
   いま触れば POLICY §26「『良さそう』で出荷しない」に反する。
4. 計測が週内に回復したら、優先順位を POLICY §2 の通り
   「実験の結論処理 → エラー修正 → ガードレール外の性能・安定性 → BACKLOG 最上位」に戻す。

1. **【最優先】テレメトリが届いているかを人間が 1 度だけ確認してほしい。**
